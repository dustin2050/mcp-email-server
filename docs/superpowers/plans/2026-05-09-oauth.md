# OAuth 2.1 Implementation Plan

> **For agentic workers:** execute this plan strictly task-by-task. Every task follows the same loop: write a failing test, confirm the failure, implement the smallest change, run `uv run pytest -q --tb=short 2>&1 | tail -20`, then commit before starting the next task.

**Goal:** Add OAuth 2.1 authentication for HTTP transports in `mcp-email-server`, keep `stdio` unchanged, expose Railway-friendly health checks, and document the deployment flow.

**Architecture:** new `mcp_email_server/oauth.py` module containing `MCPOAuthProvider` plus env/config helpers; minimal wiring in `mcp_email_server/app.py` and `mcp_email_server/cli.py`; focused tests in `tests/test_oauth.py`, `tests/test_oauth_integration.py`, and `tests/test_cli.py`.

**Tech Stack:** Python 3.10+, FastMCP, Starlette, `mcp[cli]`, `pytest`, `pytest-asyncio`, `httpx`.

---

## Verified Repo Decisions

1. `mcp_email_server/app.py` currently creates a module-level `FastMCP("email")` instance and registers tools directly on it. OAuth wiring should therefore be additive, not a full app-factory rewrite.
2. `mcp_email_server/cli.py` already centralizes HTTP transport setup in `_configure_http_transport(host, port)`. This is the correct place to add warning and auth wiring for `sse` and `streamable-http`.
3. The installed `mcp` library differs from the task shorthand: `AuthSettings` requires both `issuer_url` and `resource_server_url`. The implementation must set `resource_server_url = MCP_PUBLIC_URL.rstrip('/') + '/mcp'`.
4. FastMCP already exposes `custom_route(...)`, so `/healthz` can be added without wrapping the app in another framework.
5. The installed auth handler already enforces `code_challenge_method == "S256"` and verifies `code_verifier` against the stored challenge. The provider only needs to store the challenge and validate its shape.
6. Baseline before any OAuth work: `238 passed` from `uv run pytest -q --tb=no`.
